## 本轮改动

按「软件本质还是听歌、下载，优化不要跟现有工程冲突」的口径，
**只修批量入队瞬间的性能，行为等价、UI 版式与数据源一律不动**：

- 根因：`下载全部` 对每首歌循环调 `enqueue(song)`，而每首都做
  `persist()`（`JSON.stringify` 整队列 + `Store.flushSync()` 同步刷盘）、
  `notify()`（AppStorage 全局广播全量重绘）、`pump()`，再加线性查重与 `unshift` 头插的 O(n²)。
  加 100 首 = 100 次同步磁盘 IO 压在 UI 线程 + 100 次全量重绘 + 累计 5050 个 task 的序列化
  —— 这正是「不卡死、但巨卡」的典型特征。删除路径 `removeMany()` 早已收口，添加路径漏了。
- 修复：`Downloader.enqueueAll` 重写为真批量（一次 `Set` 索引查重、一次整体前插、
  **persist / notify / pump 各一次**）；`enqueue` 单首委托它，单曲行为完全等价。
- 两个批量入口（歌单「下载全部」、音源页试跑「下载全部」）整批入队；
  歌单侧**保留 `hasDownload()`**（它还查本地音乐库，删了本地歌会被重下）。
- 单首下载入口、UI 版式、路由、数据源、`Store` 落盘底座、`removeMany`、并发档位全部照旧。
- 量化（N=100，按真实代码结构复算）：同步刷盘 `100→1`、全局广播 `100→1`、
  累计序列化约 50 倍下降、O(n²) 线性比较与头插搬移归零；N=1 前后完全一致。
