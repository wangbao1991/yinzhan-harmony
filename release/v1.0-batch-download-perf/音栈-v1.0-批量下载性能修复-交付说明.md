# 音栈 v1.0 · 累计交付说明（本轮：批量下载性能修复）

> 基线：`v1.0f` 交接包 / `com.yinzhan.music` / `versionCode 67` / `versionName 1.0`
> 本轮日期：2026-11-15　|　构建：HarmonyOS API 26 release　|　自检：`81 项：PASS 79 / WARN 2 / FAIL 0`
> 本轮只做一件事：**修好「一次添加几十 / 上百首下载会巨卡」**。纯性能改动，功能行为等价，
> 不碰 UI 版式、不新增路由、不碰数据源、不动下载落盘底座——与既定「不跟现有工程冲突」边界一致。

## 一、本轮需求（用户口径原文）

> 「现在开始，能不能把这个软件优化一下性能？如果我一下子添加几十首歌，上百首歌下载的情况，
> 就会卡，不是说卡死，反正就是巨卡。按说我们这个软件应该算是轻量软件了，怎么会这样？」

问题定性：**不是软件重，是批量入队没有收口**。「不卡死、只是巨卡」是很典型的特征——
每一首都能做完，只是把单首的成本放大了 N 倍，且其中一步是**同步磁盘 IO 压在 UI 线程**。

---

## 二、为什么会卡（根因链，已逐行核实）

改动前的批量下载链路：`downloadAll()` / `下载全部` → 对每首歌循环调 `enqueue(song)`，
而 `enqueueAll(songs)` 本身也只是 `for (song) enqueue(song)`。**每一首 `enqueue` 都做这一整套：**

| 每加一首就执行一次 | 代价 | 加 100 首的后果 |
|---|---|---|
| `persist()` → `JSON.stringify(整个队列)` → `Store.put` → **`flushSync()` 同步刷盘** | 队列越长，序列化越大；同步写盘阻塞 UI 线程 | 累计约 **5050 个 task** 的序列化量、**100 次同步磁盘 IO** |
| `notify()` → `AppStorage.setOrCreate('downloadVersion')` **全局广播** | 所有订阅组件重绘 | 首页、下载页、**每个任务行**、歌单页、播放页、歌曲行 → **全量重排 100 次** |
| `find()` 查重 + 第二个 `for` 查 running/waiting + `tasks.unshift()` 头插 | 每次 O(n) 遍历 + 数组搬移 | 查重 / 搬移累计 **O(n²)** |
| 外层 `downloadAll()` 每首还调一次 `hasDownload()` | 又两次线性遍历 | 再叠一层 O(n²) |

**最致命的是 `flushSync()`**：`Store.put` 用 `putSync + flushSync` 同步落盘，这是当初为
「登录态不丢」定的红线（有自检断言锁着，**底座不能动**）。批量时被触发 100 次，UI 线程被
磁盘写反复阻塞——这正是「不卡死但巨卡」的来源。

**代码里自带的反证**：`Downloader.removeMany()` 的注释白纸黑字写着
> 「批量删除：只落盘一次、广播一次，避免删 20 条刷 20 遍列表」

也就是说，**删除路径早就做过批量收口，添加路径漏了**；`enqueueAll()` 这个方法虽然存在，
内部却是逐首 `enqueue`，形同虚设，三个批量入口还各写各的循环、压根没用它。

所以答案很直接：软件依然是轻量的，卡的是**一处 O(n²) 且带 N 次同步 IO 的实现缺陷**，与架构无关。

## 三、具体改动（4 个源码文件 + 1 个自检文件，行为等价）

### 3.1 `core/Downloader.ets` — 批量入队单次收口（核心）

`enqueueAll(songs, quality?)` 重写为**真正的批量实现**：

- 一次 `Set<string>` 建索引（done / running / waiting 都算已存在）→ 查重从 O(n²) 降为 O(n)；
  批内重复 id 也只留一首；音质档一批只取一次。
- `fresh[]` 正序 `push` 进 `queue` —— `pump()` 用 `shift()`，**先下先加的顺序不变**；
  `head[]` 倒序 + `head.concat(this.tasks)` **一次整体前插**，保持「后加的显示在最前」的
  既有展示顺序，替代 O(n²) 的逐首 `unshift`。
- **`persist()` / `notify()` / `pump()` 各只一次**：整批只落盘一次、只广播一次、只补位一次。
- 返回真实入队数量（原来返回的是循环次数，含被去重的），toast 数字更准确。

`enqueue(song, quality)` 改为**委托 `enqueueAll([song], quality)`**：单曲行为完全等价
（同样是查重 → 落盘 → 广播 → 补位各一次），但单曲 / 批量只剩一条实现，不会分叉。
签名不变，所有单首调用点零改动。

### 3.2 `ui/pages/SheetDetailPage.ets` — 歌单「下载全部」

先在内存里筛出 `pending[]`（保留 `hasDownload()` 与 `source !== 'local'` 判断），再整批
`enqueueAll(pending)`。**`hasDownload()` 必须保留**：它还查本地音乐库（`local.pathOf()`），
删了会让本地已导入的歌被重新下载；它只是纯内存比较、不触发 IO / 广播，留着无妨。

### 3.3 `ui/pages/SourcesPage.ets` — 音源能力试跑「下载全部」

循环逐首 `enqueue` 改为整批 `enqueueAll(this.cfgSongs)`。

### 3.4 单首下载入口一个没动

`App.ets` 听够 2/3 自动下载、`PlayerPage` 底栏下载、`SongMenu`、`Common` 歌曲行下载，
仍走 `enqueue(song)`，行为不变。

### 3.5 `scripts/selfcheck.py` — 新增 `DC` 组 + 一处断言适配（如实说明）

- 新增 **`DC` 组（8 类断言）**：锁死 `enqueueAll` 内 persist/notify/pump 各恰好一次、
  Set 索引查重 + 一次整体前插、单首委托批量、两个批量入口整批入队、单首出口保持不变、
  `Store` 落盘底座 / `removeMany` / 取消·重试·清理·并发档位 / `hasDownload` 过滤不回退、
  零新增路由。
- **一处既有断言适配**：`DB` 组原有一条把 `App.get().downloads.enqueue(song)` 写死成字面量
  （校验「试跑结果走既有下载出口」）。改批量后该字面量消失，因此**只把匹配放宽为前缀
  `App.get().downloads.enqueue`**——单首与批量都算「走下载出口」，**检查意图不变、断言没删、
  没有降低强度**；批量收口的严格约束由新增的 `DC` 组专门承担。

`AGENTS.md` 已追加本轮「接手必读」节（根因链、红线、别再写回逐首循环的提醒）。

## 四、量化效果（按真实代码结构等价复算，非真机跑分）

以「一次批量加 N 首」计，进入下载页时队列为空：

| N | 同步刷盘(次) 前→后 | 全局广播(次) 前→后 | 累计序列化 task(个) 前→后 | 线性比较(次) 前→后 | 头插搬移(个) 前→后 |
|---|---|---|---|---|---|
| 10 | 10 → **1** | 10 → **1** | 55 → **10** | 90 → **0** | 45 → **0** |
| 30 | 30 → **1** | 30 → **1** | 465 → **30** | 870 → **0** | 435 → **0** |
| 50 | 50 → **1** | 50 → **1** | 1275 → **50** | 2450 → **0** | 1225 → **0** |
| 100 | 100 → **1** | 100 → **1** | 5050 → **100** | 9900 → **0** | 4950 → **0** |
| 200 | 200 → **1** | 200 → **1** | 20100 → **200** | 39800 → **0** | 19900 → **0** |

**N=100 小结**：同步刷盘 `100 → 1`（降为 1/100）、全局广播 `100 → 1`（降为 1/100）、
累计序列化约 **50 倍**、线性比较与头插搬移的 O(n²) 项**完全消除**。
N=1（单首下载）前后完全一致，行为等价。

> 说明：以上是对源码中确定的循环 / 调用关系做等价复算，用来量化「为什么会卡」与
> 「改善幅度」，**不是真机帧率测试**。沙箱无设备，真机体感请以装机实测为准。

## 八、已知限制（如实告知）

- **未上真机**：沙箱无 HarmonyOS 设备。已做到静态断言、逻辑复算、API 26 编译、交付 zip
  全新解压复现、HAP 内部逐文件比对；**卡顿是否完全消失、大体量下的体感，仍需真机实测**。
- 本轮只修「**批量入队瞬间**」的卡顿。下载进行中，每首任务完成 / 失败仍各自
  `persist()` + `notify()`，进度广播有 300ms 节流；这是**离散在时间轴上**的必要状态刷新，
  不会形成入队瞬间的风暴，故未改动。若真机上「下载过程中」仍觉得掉帧，可另行排查。
- `Store` 的 `putSync + flushSync` 同步落盘底座**按红线保留不动**，本轮只把调用次数从 N 降到 1。
- 「同时下载几首」并发档位（默认 3，1~5）不变；本轮不改变下载并发行为。
- HAP 为 unsigned，装机需签名；源码包按铁律不含任何签名材料。
