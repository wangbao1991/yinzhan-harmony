**基线**：`音栈-交接包-20261114-v1.0f.zip`（`com.yinzhan.music` / `versionCode 67` / `versionName 1.0`）
**日期**：2026-11-14
**说明**：文件名从上版 `音栈-v1.0-歌曲评论-*` 改为 `音栈-v1.0-音源能力扩展-*`，但仍是**累计包**：
歌曲评论（四平台 + 无限滚动）、失败面板对比度、听够 2/3 自动下载、QQ / 网易云账号等历史功能全部包含，
再加本轮的「音源能力扩展」。四个交付物为本轮全新产物，SHA 全部变化。

## 一、本轮需求与边界（用户口径原文）

> 「我说的扩大范围，意思是支持音源的能力。」
>
> 「你刚刚说发现页之类专辑什么之类的，现在有。如果做了之后，会不会跟现在的冲突？
> 我的想法是，软件能支持更多的音源，也能把音源要求的东西给它适配。但是最好不要跟现有工程冲突，
> 这个软件的目的本质不还是听歌、下载。」

按此收敛，本轮**只补音源运行时能力 + 音源脚本要求的配置**，不新增内容页：

| 会冲突（明确**不做**） | 不冲突（本轮**只做**） |
|---|---|
| 把插件的榜单 / 专辑 / 推荐歌单混进发现页、榜单页、专辑详情、搜索页 | 补齐音源运行时对脚本导出能力的支持（8 类高频能力） |
| 改内容页数据源与版式、新增路由 | 把音源要求的 `userVariables` / cookie / token / apikey / 自建地址给它 |
| 新增独立「能力页 / 广场页」 | 落点**只在音源管理页**既有 `bindSheet` 菜单 |
| 把试跑结果接成新的浏览页 | 结果**只进既有播放 / 下载出口** |

**目标没有变**：配置给全 → 取链成功率上去 → 能放能下。软件的本质仍是听歌、下载。

具体红线（自检 `DB` 组锁死）：**零新增路由**（路由表仍 12 个名字）、**内容页零改动**、
`actions` 协议三值 `musicUrl / lyric / musicSearch` 不变（扩展能力走独立 action，不污染取链 / 取词）、
既有 selfcheck 断言一条不动、`webdav` / `pako` 继续如实标注不支持。

## 二、为什么是「能力层」，不是「数据层」

调研阶段在 GitHub / 网页检索到 **243 份真实音源样本**（洛雪 50 / MusicFree 193），逐份用工程里的
`MFRuntime.load()` 真实装载后统计实际导出能力。结论：

- 装载层基本无缺口；`detectKind` 双端规则量化验证过 186 份插件本体，旧规则只漏判 1 个洛雪脚本，
  新增特征无收益 → **未改判定规则**。
- 真正的缺口在 **MusicFree 插件的高频能力没有被运行时接通**（插件导出了，App 没有对应分派），
  以及 `env.getUserVariables()` 被写死成 `{}`，导致要求 cookie / token / apikey / 自建地址的插件拿不到配置。

按实际导出统计（193 份 MusicFree 插件）：

| 能力 | 导出份数 | 本轮是否接通 |
|---|---|---|
| `musicSearch` 搜歌 | 174 | 既有（保持不变） |
| `lyric` 歌词 | 141 | 既有（保持不变） |
| `topLists` / `topListDetail` 榜单 | 136 / 136 | **本轮新增** |
| `albumInfo` 专辑详情 | 109 | **本轮新增** |
| `albumSearch` 搜专辑 | 106 | **本轮新增** |
| `importSheet` 导入歌单 | 94 | **本轮新增** |
| `sheetInfo` / `artistWorks` | 90 / 89 | 既有链路覆盖 |
| `recommendSheets` / `recommendTags` | 81 / 80 | **本轮新增** |
| `musicInfo` 单曲信息 | 63 | **本轮新增** |

其中 32 份插件声明了用户变量、需要填配置才能正常工作——这正是「把音源要求的东西给它适配」的落点。

## 三、具体改动

### 3.1 运行时 `mf_runtime.js`：8 类能力真实分派

新增 `albumSearch / albumInfo / topLists / topListDetail / recommendTags / recommendSheets / musicInfo / importSheet`
八类 action 分派，兼容 `getRecommendSheetsByTag` 变体，配套归一辅助
`listOf / endOf / toTag / toTopSheet / flattenTopLists / fromSongs`（`fromSongs` 放 `makeRequest` 内部，
依赖 `listOf/endOf`）。

- `importSheet` 调插件真实 `importMusicSheet(urlLike)`，异常作为**真实失败原因**回传，不拿空列表冒充成功。
- `load()` 按**实际导出**生成 `capabilities` 与 `variableDefs`，不造能力。
- `actions` 协议三值不变，扩展能力走独立 action，取链 / 取词链路零改动。
- `webdav` / `pako` 保留 `notSupported(...)`。

### 3.2 `env.getUserVariables()`：从写死 `{}` 到真实值 + 即时生效

```js
function readUserVars() {
  if (varsGetter !== null) {
    try { var v = varsGetter(); if (v && typeof v === 'object') return v; }
    catch (e) { /* 宿主未就绪时退回静态值 */ }
  }
  return varsStatic;
}
var env = {
  getUserVariables: readUserVars,   // getter：保存配置后即时生效，不必重载脚本
  userVariables: readUserVars(),    // 兼容插件直接读属性
  AG_DEBUG: false, appVersion: '1.0', os: 'android', lang: 'zh-CN'
};
```

Node 侧验证：保存前读 `AAA`、保存后读 `BBB`，确认 getter 生效。

### 3.3 用户变量：按音源实例隔离，只存本机

- `PrefKeys.MF_USER_VARS = 'v4_mf_user_vars_'` + `sourceId`，不同音源互不串配置。
- **含凭证，不进 `Backup` 白名单**：换机不串账号、不随备份外泄。
- `lx_bridge.html` 用 `userVarsByInst` 按实例隔离；`__unload` / `__reset` 清变量防串源；
  host 新增 `__setUserVars(instId, varsJson)`。
- `LxRunner.load()` 把 `window.__setUserVars(...)` 与 `window.__load(...)` **合并进同一次 `runJavaScript`**
  （`LxRunner.load` 签名不变），确保插件顶层读取时值已就位；新增 `setUserVars()` 供保存后即时注入。

### 3.4 宿主侧与 UI 落点

| 文件 | 改动 |
|---|---|
| `lx_bridge.html` | `userVarsByInst`、`__setUserVars`、`loaded` 消息带 `meta`（capabilities + variableDefs）、卸载/重置清变量 |
| `core/LxRunner.ets` | `NativeMessage.meta?` + `onMeta` 回调、`userVars: Map`、变量注入与 `load` 合并、`setUserVars()` |
| `common/Models.ets` | 新增 `MfVarDef / MfMeta / MfProbeResult` |
| `common/Constants.ets` | 新增 `PrefKeys.MF_USER_VARS` |
| `core/SourceRepo.ets` | `mfMetaOf()` / `mfUserVars()` / `saveMfUserVars()` / `injectUserVars()` / `probeMf()`；`loadAll` / `loadOne` 装载前注入变量 |
| `ui/pages/SourcesPage.ets` | 菜单新增「配置与能力」（仅 MusicFree 源显示）：查看真实能力、填变量、能力试跑；试跑结果只进播放 / 下载 |
| `scripts/selfcheck.py` | 新增 `DB` 组，锁死能力分派、变量链路、UI 落点、内容页零改动、零新增路由 |
| `AGENTS.md` | 追加本轮接手必读节（口径、红线、链路、踩坑） |

**结果只进既有出口**，没有新增任何浏览页：

```ts
App.get().playAndOpen(this.cfgSongs.slice(), 0);   // 播放
App.get().downloads.enqueue(song);                // 下载
```

> 命名坑：新实例方法叫 `mfMetaOf`，不能叫 `mfMeta`（与既有静态方法 `mfMeta(code, key)` 撞名）。
> ArkTS 坑：`capLabel()` 里 `Record<string, string>` 的键必须写成字符串字面量 `'musicSearch': '搜歌曲'`，
> 否则 `arkts-no-untyped-obj-literals` 编译报错（曾卡在 `SourcesPage.ets:1263`）。

## 七、使用步骤

1. 安装（需自行签名）。既有功能（评论、自动下载、账号同步、取链下载）用法不变。
2. **给音源填配置**：音源管理 → 点音源卡片菜单 →「配置与能力」→ 看它真正导出了哪些能力 →
   按字段填 cookie / token / apikey / 自建地址 → 保存。**保存后即时生效，不用重载脚本**。
3. **能力试跑**：同一面板里选一个能力（如「导入歌单」「榜单歌曲」「搜专辑」）、输入关键词 → 试跑 →
   结果可「播放」或「加入下载队列」，走的就是原本的播放 / 下载流程。
4. **导入更多音源**：打开订阅清单，复制 raw 直链（国内网络可用 proxy 形式）→ 音源管理右上「+」→「从网络导入」。

## 八、已知限制（如实告知）

1. **本轮改动未上真机**：沙箱无设备，只做到运行时 Node 侧真实装载验证 + 静态断言 + 编译 + 交付 zip 全新解压复现。
   ArkWeb 沙箱里 `env.getUserVariables` getter 的真机行为、各插件真实取链效果需装机确认。
2. **能力试跑结果不落内容页**：按边界要求，试跑结果只在音源页面板内展示并进播放 / 下载出口，
   不会出现在发现页 / 榜单页 / 专辑页。想听、想下才用，不改造既有浏览体验。
3. **用户变量只存本机、不进备份**：换机 / 重装后需重新填写；这是为避免凭证随备份外泄的有意设计。
4. **15 份音源装载失败是样本自身问题**（依赖缺失 / 重复声明等），非本轮改动引入，清单中已如实标注。
5. **v4 独家音源不可用是外部原因**：文件被作者删除、服务端停用 v4。工程已能导入解析 LX 音源，按用户决定不改音源代码。
6. **构建脚本口径**：v1.0f 基线按「省空间」要求移除了 `archive/baseline/音栈-v2.48-基线.hap`，
   `build_release.sh` 的 `[0/5]` 固定哈希校验会中止、`make_source_zip.sh` 内容自检也会报该项缺失。
   这是**基线既有状态**，本轮未擅自补回。直接用 `hvigorw` 构建（三处均已实测通过）：

```bash
export PATH=/opt/harmonyos/command-line-tools-26/bin:/opt/harmonyos/command-line-tools-26/tool/node/bin:$PATH
export DEVECO_SDK_HOME=/opt/harmonyos/command-line-tools-26/sdk
export DEVECO_NODE_HOME=/opt/harmonyos/command-line-tools-26/tool/node
hvigorw assembleHap --mode module -p product=default -p buildMode=release --no-daemon
```
