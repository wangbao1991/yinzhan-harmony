# 编译环境重建指南（避坑版）

> 这份文档属于源码工程本身，随 `LXMusicHarmony/` 一起交付。**拿到工程目录，不用华为账号、不用 DevEco Studio 图形界面，就能重建出可编译、可签名的 HarmonyOS 7.0 / OpenHarmony 7.0-Release（API 26）命令行环境。**
>
> 工程自 v2.7 起使用 API 26 并行工具链（`compatibleSdkVersion 26.0.0` / hvigor 6.26.4 / JDK 17+）。旧的 API 12 工具链**不能**构建本工程，会因 SDK 版本不匹配直接失败。
>
> 原始依据见同目录 `参考-编译环境搭建手册.md`；本文记录的是按该手册实际复现时**踩过的五个坑**以及验证通过的免登录重建方案。

---

## 0. 为什么需要「重建」而不是「照着官网装」

手册给的官方路径是下载官方 command-line-tools。实测两个硬阻碍：

- 华为下载页 `https://developer.huawei.com/consumer/cn/download/command-line-tools-for-hmos` 的下载接口**需要华为账号登录态**；
- CDN 直链带 `HW-CC-Date` / `HW-CC-Sign` 时效签名，几小时后过期，历史链接全部 403，**不能把直链写死进脚本**。

所以本文改用三个**可匿名访问**的公开源，拼装出与官方 CLT 等价的工具链，并在全新目录里重跑过一遍，确认可复现。

## 1. 快速开始（三条命令）

以下命令均在**工程根目录** `LXMusicHarmony/` 执行：

```bash
bash scripts/env/setup_env_26.sh     # ① 首次搭建（约 3 GB 下载，装完约 6 GB）
source scripts/env/env.sh            # ② 载入环境变量（每个新终端都要执行一次）
bash scripts/env/build_release.sh    # ③ 基线复核 → 构建 → 签名 → 验签 → 版本核对 → 自检
```

第三条跑完会打印 `全部通过。产物：build/音栈-v2.48-signed.hap`。

> 源码工程包**不含任何签名材料**（`signing/` 下的 `.pem` / `.p7b` / `.cer` 已剔除，云构建平台会以 `HK-PROJECT-SECRET-FILE` 拒绝归档含证书的工程）。没有材料时脚本自动降级：照常构建、版本核对、自检，输出 **unsigned HAP** 并提示「跳过本地签名」，不会报错中断。要本地签名就把自己的 `app-chain.pem` + `profile.p7b` 放进 `signing/`，脚本会自动走签名分支。

无 root 权限时把工具链装到自己的目录，脚本会自动记住位置：

```bash
CLT_DIR=$HOME/harmonyos/command-line-tools-26 bash scripts/env/setup_env_26.sh
source scripts/env/env.sh
bash scripts/env/build_release.sh
```

`setup_env_26.sh` 会把 `CLT_DIR` 与 `JAVA_HOME` 写进工程根的 `.env.local`，`env.sh` 自动读取；该文件是本机产物，**不要提交到版本库、不要打进源码包**。换机器后删掉它、重跑一次 `setup_env_26.sh` 即可。

只想手工分步也可以：

```bash
source scripts/env/env.sh
rm -rf entry/build
hvigorw assembleHap --mode module -p product=default -p buildMode=release --no-daemon
bash scripts/sign_hap.sh \
  entry/build/default/outputs/default/entry-default-unsigned.hap \
  build/音栈-v2.48-signed.hap
python3 scripts/selfcheck.py
```

## 2. 两条搭建路径

### 路径 A：官方 Command Line Tools（本机开发，需华为账号）

下载页选与 API 26 配套的 **Command Line Tools for HarmonyOS 7.0 Release / Linux x64**，解压后：

```bash
export CLT_DIR=/path/to/command-line-tools
source scripts/env/env.sh     # 会按 CLT_DIR 指向官方工具链
```

官方包里的 `bin/hvigorw`、`sdk/`、`tool/node/` 结构与本文重建结果一致，后续构建命令完全相同。Windows / macOS 直接用 DevEco Studio 图形界面（Settings → SDK 勾 API 26）更省事。

> 注意：`env.sh` 会对 `sdk/default/sdk-pkg.json` 里的 `apiVersion` 做软校验，指到 API 12 工具链会打印警告并提示重建，避免用了错的 SDK 还以为工程坏了。

### 路径 B：免登录重建（CI / 沙箱 / 无账号，推荐）

| 组件 | 地址 | 说明 |
| --- | --- | --- |
| OpenHarmony 7.0-Release 公开 SDK | `https://repo.huaweicloud.com/openharmony/os/7.0-Release/ohos-sdk-windows_linux-public.tar.gz` | 约 3 GB，内含 `*-linux-x64-26.0.0.38-Beta.zip` 五个组件 |
| `@ohos/hvigor` | `https://repo.harmonyos.com/npm/@ohos/hvigor/-/hvigor-6.26.4.tgz` | **自带全部依赖** |
| `@ohos/hvigor-ohos-plugin` | `https://repo.harmonyos.com/npm/@ohos/hvigor-ohos-plugin/-/hvigor-ohos-plugin-6.26.4.tgz` | 自带依赖 |

锁定 `hvigor 6.26.4` + `hvigor-ohos-plugin 6.26.4` + `SDK 26.0.0.38 (API 26)`。不要随意升版本：插件与 SDK 的组件清单是配套的；也不要降到 5.8.x，那套对应 API 12。

前置系统依赖：`curl` `unzip` `tar` `node >= 14.19`（实测 Node 22）`java`（JDK 17+，推荐 21）`python3`（构建流水线与自检用）。

## 3. 工具链目录布局

```
$CLT_DIR/                                   # 默认 /opt/harmonyos/command-line-tools-26
├── bin/hvigorw                            # 构建入口（重写的 wrapper，设置 NODE_PATH / SDK / NODE_HOME）
├── tool/node/bin/{node,npm,npx}           # 软链到系统 Node
├── hvigor/
│   ├── hvigor/                            # @ohos/hvigor 6.26.4
│   ├── hvigor-ohos-plugin/                # @ohos/hvigor-ohos-plugin 6.26.4
│   └── node_modules/@ohos/                # 两个包的作用域软链
└── sdk/default/
    ├── sdk-pkg.json                       # 组件清单元数据（格式见第 4 节）
    ├── openharmony/{ets,js,native,previewer,toolchains}/
    │   └── toolchains/lib/{hap-sign-tool.jar,OpenHarmony.p12}
    └── hms/{ets,js,native,previewer,toolchains}/   # 空占位 + uni-package.json
        ├── toolchains/{modulecheck,configcheck,syscapcheck}/  # 配置校验 schema（见坑 4）
        └── toolchains/lib/libimage_transcoder_shared.so       # 闭源库占位（见坑 5）
```

**工程侧零依赖**：`oh-package.json5`、`entry/oh-package.json5`、`hvigor/hvigor-config.json5` 的 `dependencies` 全为空。不需要 `ohpm install`、不需要 `node_modules`，**可完全离线构建**（依赖只在首次搭环境时联网下载）。

`env.sh` 导出的变量：`COMMANDLINE_TOOL_DIR`、`DEVECO_SDK_HOME`、`DEVECO_NODE_HOME`、`JAVA_HOME`、`OHOS_SDK_LIB`、`NODE_PATH`。工程自带的 `scripts/build.sh` 只依赖 `COMMANDLINE_TOOL_DIR`，因此 `source scripts/env/env.sh` 之后也能直接用它（注意它是 debug 模式，且不做签名）。

## 4. 五个关键避坑点

### 坑 1 · `sdk-pkg.json` 必须是「单组件」格式

`HosLocalComponentLoader` 把该文件当作**一个组件**解析，读 `data.path / data.version / data.apiVersion`。写成组件数组会解析出空组件表：

```
hvigor ERROR: SDK component missing. Please verify the integrity of your SDK.
```

✅ 正确（`setup_env_26.sh` 里已按此生成）：

```json
{
  "meta": { "version": "3.0.0" },
  "data": {
    "apiVersion": "26",
    "displayName": "HarmonyOS 7.0.0 (OpenHarmony 7.0-Release)",
    "path": "default",
    "version": "26.0.0.38",
    "releaseType": "Beta",
    "platformVersion": "26.0.0",
    "stage": "Beta"
  }
}
```

扫描器据此自动派生 `openharmony/{ets,js,native,previewer,toolchains}` 与 `hms/{ets,native,previewer,toolchains}` 两组组件条目。

### 坑 2 · `hms/` 只能是空占位，不能软链到 `openharmony/`

hvigor 会同时校验 OHOS 与 HMS 组件；HMS 侧只检查 `uni-package.json` 是否存在。第一版图省事把 `hms/ets` 等软链到 `openharmony/ets`，restool 因此重复加载系统资源：

```
Error: 'ohos_id_color_foreground' and 'ohos_id_color_foreground' defind the same ID.
```

✅ 正确做法：**真实空目录 + 一个 `uni-package.json`**（内容从对应 `openharmony/<组件>/oh-uni-package.json` 复制）。本工程不使用 HMS 专属 Kit，空目录不影响 ArkTS 编译。

### 坑 3 · hvigor tarball 已 vendor 全部依赖，别用 `npm install`

两个 tarball 内含 `node_modules`，包括**未公开发布**的 `@baize/wdk`、`@ohos/hvigor-arkts-base` 等。公共 registry 上 `@baize/wdk` 是 404，任何 `npm install @ohos/hvigor-ohos-plugin` 的方案都会失败。

✅ 正确做法：直接解包官方 tarball，再在 `hvigor/node_modules/@ohos/` 下建两个作用域软链，让 `hvigorfile.ts` 的 `import` 能解析。

> 顺带一个容易误判的点：`build-profile.json5` 的 `signingConfigs` 为空是**设计如此**，日志里的 `Will skip sign 'hos_hap'` 不是错误。hvigor 产出 unsigned HAP，签名由 `scripts/sign_hap.sh` 单独完成。

### 坑 4 · `hms/toolchains` 还要补齐配置校验 schema

HMS 侧的 toolchains 不只是「存在性占位」：`getAppSchema()` / `getModuleSchema()` 指向
`hms/toolchains/modulecheck/{app,module}.json`，PreBuild 用它校验 `app.json5` / `module.json5`。
只改 `.ets` 或图片资源时该校验可能走缓存不触发，**一旦改了 `module.json5`**（例如换启动图标）
就会立刻暴露：

```
hvigor ERROR: Failed :entry:default@PreBuild...
hvigor ERROR: .../hms/toolchains/modulecheck/app.json: ENOENT: no such file or directory
hvigor ERROR: BUILD FAILED in 4 s
```

✅ 正确做法：把 `openharmony/toolchains` 下的 `modulecheck`、`configcheck`、`syscapcheck`
三个**纯 JSON 校验目录**复制进 `hms/toolchains/`。`setup_env_26.sh` 已自动完成，并在验证段检查
`modulecheck/app.json` 是否存在。

这与坑 2 不冲突：那三个目录只有 schema 文件、不含系统资源，不会引起 restool 重复加载；
**不要**因此把整个 `hms/` 软链到 `openharmony/`。

### 坑 5 · API 26 的 restool 会无条件 dlopen 闭源图片转码库

API 26 / hvigor 6.26.4 的 `CompileResource` 会把 `optCompression.context.extensionPath`
传给 restool，restool 随即 `dlopen` `hms/toolchains/lib/libimage_transcoder_shared.so` ——
**即使工程完全没有配置图片压缩**。该库属闭源 HMS 组件，OpenHarmony 公开 SDK 里不存在：

```
Error 11201001 / Failed to load the library ... path invalid
```

✅ 正确做法：放一个零依赖的标准共享库占位（`setup_env_26.sh` 复制系统 `libz.so.1`）。
工程未配置 `resOptions.compression`，restool 只 `dlopen`、不会调用转码符号，占位库足够；
这只是补公开 SDK 的缺口，不冒充任何鸿蒙组件。若你的机器上找不到 `libz.so.1`，脚本会明确报错并提示手工放置。

## 5. 常见报错速查

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `SDK component missing` | `sdk-pkg.json` 格式错，或 `DEVECO_SDK_HOME` 指错 | 见坑 1；确认指向 `<CLT_DIR>/sdk` |
| `'ohos_id_color_foreground' ... same ID` | hms 组件与 openharmony 内容重复 | 见坑 2，改成空占位目录 |
| `@baize/wdk 404` | 用 npm 从公共源装插件 | 见坑 3，改用官方 tarball |
| `Failed :entry:default@PreBuild ... modulecheck/app.json ENOENT` | 改了配置文件，HMS 侧缺校验 schema | 见坑 4，补齐三个 check 目录 |
| `Error 11201001` / `Failed to load the library ... libimage_transcoder_shared.so` | 公开 SDK 缺闭源转码库 | 见坑 5，放占位 `.so` |
| 提示 `compatibleSdkVersion 26.0.0` 与 SDK 不匹配 | 用了 API 12 工具链 | 重跑 `setup_env_26.sh`，确认 `sdk-pkg.json` 的 `apiVersion` 为 `26` |
| `Cannot find module '@ohos/hvigor-ohos-plugin'` | 插件软链缺失 | 确认 `hvigor/node_modules/@ohos/` 下两个软链存在 |
| `hvigorw: command not found` | 没载入环境 | `source scripts/env/env.sh` |
| 未找到 `hap-sign-tool.jar` | `OHOS_SDK_LIB` 指错 | 应指向 `.../sdk/default/openharmony/toolchains/lib` |
| `Will skip sign 'hos_hap'` | `signingConfigs` 为空（正常） | 用 `scripts/sign_hap.sh` 单独签名 |
| `install parse profile prop check fail` | 改了 `bundleName` 却没重签 `profile.p7b` | 按参考手册第六节重签 profile |
| JDK 相关异常 | API 26 工具链推荐 JDK 21 | 装 21；17 以上实测可用 |
| `device type 'phone' is not supported` | SDK 元数据提示，WARN | 忽略，工程按手册保持 `phone/tablet/2in1` |
| 构建中止并打印「基线 HAP 哈希不符」 | `archive/baseline/音栈-v2.48-基线.hap` 被改动 | 恢复原始基线文件；这是防篡改断言，不要改脚本哈希迁就 |

## 8. 签名与真机提醒

`scripts/sign_hap.sh` 用的是 **OpenHarmony 公共签名材料**（`OpenHarmony.p12` + 随包 profile），适用于 OpenHarmony 设备、模拟器与产物验收。**HarmonyOS NEXT 华为正式真机**通常需要在 DevEco Studio / AGC 里按包名 `com.yinzhan.music` 生成调试证书与 profile，替换 `signing/` 下材料后重新签名；不要直接改 `module.json` 的 `bundleName` 而不重签 profile，否则安装时会报 `install parse profile prop check fail`。

### 用云端构建中心（不上传证书）

源码包**刻意不含 `signing/`**：云构建平台会把 `.cer` / `.p12` / `.p7b` / `.pem` 一律判为敏感材料，直接拒绝归档并报 `HK-PROJECT-SECRET-FILE`。上传时按下面三步：

1. 选 **API 26**（HarmonyOS 26.0.0）——**不要选 API 24 / HarmonyOS 6.1.1**：工程 `compatibleSdkVersion` 是 `26.0.0`，用 API 24 必然构建失败。
2. 产物类型选 **HAP 安装包**，构建模式 **Release**。
3. 直接上传源码 zip，不要解压后再改目录层级（顶层保持 `LXMusicHarmony/`，JSON 配置在根级）。

云端由平台使用自己的证书签名；想拿回本地签名，把 `signing/` 材料放回工程根即可。

## 9. 复现性说明

`setup_env_26.sh` 的下载全部走公开源且带缓存（`CACHE_DIR`，默认 `/tmp/hmos26-cache`），已下载的 SDK/tarball 不会重复拉取。已在一个**全新空目录**用该脚本重建整套环境并再次 `BUILD SUCCESSFUL`，确认不依赖沙箱残留状态。若某天公开源调整路径，只需修改脚本顶部的 `SDK_URL` / `NPM_BASE` / `HVIGOR_VER` / `SDK_VER` 四个常量，其余逻辑无需改动。
