三处「明明有源，却像没源」

按 GitHub 对标报告的落地顺序，本轮做完第 1、2 步，并把第 3 步（单上下文）做成可用的最小形态。

一句话结论 不是鸿蒙不给力，是我们把「脚本执行完」当成了「可以取链」，又给兜底直连开了「探测失败也信」的口子 —— 前者让要等 rconfig 的独家源每次都白试，后者让 11 秒的试听提示音被当成整首播。

三个根因

已修试听片段当整首

  • 酷我 convert_url_with_sign 对免费/无版权歌照样回 code:200 和一个正常 URL
  • 但 data.duration 只有 11 秒，音频是一句「免费听歌权限」的提示音
  • 上一轮我给它加了「探测失败也信任」，正好把这道拦截拆了

已修加载 ≠ 就绪

  • 独家音源要先 GET /rconfig 拿签名配置，之后才注册 request 处理器
  • 我们拿到 loaded 就发 musicUrl，必然回「未注册 request 处理器」
  • 结果：选了独家源，实际每次都在用别的源补位

已修档位把源整条筛掉

  • inited 上报的 qualitys 普遍残缺（只写 128k 的源其实能给 flac）
  • 旧逻辑「这一档不在列表里就跳过」，选无损时半屏音源直接消失
  • 官方只有 4 档且不用来筛源

新的取链判定

STEP 1
筛候选

启用 + 平台匹配 + 脚本已加载。就绪的直接进候选；未就绪但在 45s 内的进等待队列。

›
STEP 2
等 inited

没有就绪源（或首选在初始化）时，最多等 8 秒。等到了再问，不再抢跑。

›
STEP 3
取链 + 探测

音质不匹配只降权不淘汰；探测判「试听片段」直接判死，其余失败按设置信任。

›
STEP 4
兜底直连

接口 duration 先过一遍，体积再过一遍。两道都过才交给播放器。

为什么还留了一条「从没上报平台的源」的口子： 20 个脚本里有 5 个（野花、野草、念心、全豆要 v4.0、屿溪终章）全文搜不到 inited， 可能是 v1 协议或者被混淆到看不出字段。它们此前同样被判「没上报平台」。 所以规则是：只要有一个就绪源，它们不参与；一个都没有时，仍然按未知平台问一遍 —— 宁可多花一次超时，也别直接告诉用户「这首歌没有可用音源」。

回归前后的直连对比

改之前探测失败 = 信任

  • 接口回 code:200 + url → 直接返回 128k mp3
  • 探测报「只有 181KB，是试听片段」→ 因为开了「默认信任」，照样返回
  • 播放器拿到的是一句人声提示，用户听到「只有一段语音」

改之后两道校验

  • 接口 duration:11 与原曲 200 秒差 10 秒以上 → 直接拒绝，连探测都省了
  • 就算接口没给 duration，探测报「试听片段」同样硬拒绝
  • 只有 403 / 超时 / 拿不到 content-length 这类判断不了的失败才继续信任

这一轮没做的

P1-5完整单上下文串行

  • 报告里那一步是「同一时刻只跑一个音源、换源就销毁重建」，要重写加载与调度，并把并发竞速改成串行
  • 没有真机回传，全量重写很可能把现在能用的多源体验弄坏；报告本身也建议先出「2~3 个源」的最小验证版
  • 本轮先落地了它的自愈半边：整页 __reset + 单源 reload + 取链失败自动重建一次

仍无解服务端那一侧

  • 星海后端 403、VIP 曲库风控、官方强混淆源的服务端签名 —— 官方客户端同样拿不到
  • 给酷我返回试听片段这件事，我们只能识别并明确提示，改不了它的授权策略
  • 以上结论来自源码核对与离线验证，未做真机抓包
