播放失败不再是一行字，同一首歌也不用每次重猜

P1 两项：失败面板 + 一键换源 · 歌 → 源亲和表。前者把「为什么没播出来」摊开给人看，后者让同一首歌第二次播放时少绕一圈。

两个问题，两个改法 失败时你看到的是一行被截断的长串，既不知道十几个源里谁还活着，也不知道还能做什么；而每次播同一首歌，都要把十几个源重新问一遍，谁先回就用谁的。前者改成逐条列 + 当场换源，后者记下「上次谁给的」。

一、失败面板：把「问了谁、为什么」摊开

改之前 一行字

  • errorText 是十几个音源的失败原因拼成的长串，播放页只能 maxLines(1)，实际看到的永远是被截断的前半句。
  • 看不出参与取链的音源有几个，也看不出首选到底怎么失败的。
  • 失败后只有「下一首」，用户没有任何「再试一次」的入口。
  • 即使备用链接池里还躺着别的音源给的地址，也没人知道、没人能用。

改之后 可查看 · 可重试

  • 顶栏错误行变成入口：「…403… 详情 ›」，点开就是完整清单。
  • 每条形如「星海聚合 / 首选 · 320k：接口返回 403（已屏蔽）」，首选用徽标标出来。
  • 底部直接给两个动作：换个音源再试（还有 N 条） / 播放下一首。
  • 换源优先消费备用池，池空才重新向所有音源取链 —— 不白添请求，也不丢已有链接。

二、这条链路是怎么串起来的

STEP 1
Resolver 留凭据

每次取链先清空 lastNotes；失败时把每条 name + text + preferred 存下来，并记下 candidateCount。凭据为空时补一条占位说明，避免面板误判。

→
STEP 2
Player 暴露动作

getFailDetails() / getAlternateCount() 读状态；retryWithAnotherSource() 先 takeAlternative()，拿不到才 reload() 重新取链。

→
STEP 3
播放页摊开

顶栏错误行可点，panel === 7 分发到 failPanel()：逐条卡片 + 两个按钮。面板开着时后台再失败会自动刷新列表。

为什么凭据为空要单独处理：取链成功、但 AVPlayer 在 prepare 阶段失败时（链接过期、防盗链校验 UA），resolve() 根本没抛错，也就没有失败记录。这时面板要如实说「链接取到了，是播放阶段失败的」，而不是假装「一个音源都没问」。

四、歌 → 源亲和：记住「上次是谁给的」

规则 只改顺序

  • 取链成功时记 歌id@平台 → sourceId，持久化到 v4_source_affinity。
  • 排序权重：健康度 ×1000 > 音质降权 +10 > 亲和 +1。所以它只在「其它条件都一样」时起作用。
  • 它失败一次就进健康度惩罚（failStreak×10），下一轮自然被压回去 —— 不会把坏源钉死。
  • 上限 500 条，超了按时间淘汰最旧的一批；写入用 putLater 交给系统合写。

边界 可关 · 可自愈

  • 只影响「先问谁」，其余音源照常并发补位，不会变成「只问一个」。
  • 音源页新增开关「记住每首歌用的音源」，默认开；关掉只是不再学习，已有记录保留。
  • Store 未就绪时不缓存空表，否则这一次进程内永远学不到东西。
  • 只有音源脚本真的给出链接时才记；酷我直连这类兜底不记。跨平台找同款记的是那首另一平台的歌（key 含平台），不会污染原歌的亲和。

五、怎么用这两个东西定位问题

你看到的现象面板告诉你什么下一步
一首歌死活不播 列表里如果人人 403 / 404，是后端风控或链接时效，不是应用误杀 点「全部体检」看是不是整批都挂了；是就换源，别反复重试
只有某个源能用但总轮不到它 它可能根本没进候选（显示「初始化超时」） 音源页点「重建」，等「已就绪」变成 1
提示「只给到 11 秒试听」 酷我直连的免费/VIP 限制，链接本身只有试听片段 换别的源，或接受标注 —— 不会再被当整首播出去
每次播放来源都不一样 说明在并发竞速，谁先回用谁 打开「记住每首歌用的音源」，同首歌第二次就会先问上次那个

构建与验签

反向验证（故意改坏，看能不能抓到）

  • 把 panel === 7 改成 panel === 99 → T 组 FAIL「失败面板没有接进分发，点了打不开」
  • 去掉 rememberSource 里的开关判断 → U 组 FAIL「关掉后仍在偷偷写盘」

还剩什么没做：P2 的两项 —— 请求取消 + 连接复用、下载断点续传 + 失败换源。前者要桥接层透传 requestId，后者要动下载器状态机，都建议等真机跑一轮、确认瓶颈在 HTTP 还是脚本本身之后再动。
