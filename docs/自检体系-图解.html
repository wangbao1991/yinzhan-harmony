三种自检，各回答一个问题

原来的单源自检保留不动，新增「全部自检」和可开关的「启动自动自检」。三者不是替代关系，成本与结论精度完全不同。

先记住一句话 想知道「这个源能不能给某个平台的歌」→ 单源自检；想知道「我装的这些源哪个能给什么」→ 全部自检；只想快速排掉死源 → 快速体检。自动自检走的是最轻的那条。

一、三条路径的分工

入口怎么跑回答什么问题代价
单源「自检」
原有，保留		 对该源遍历三首基准曲（酷我 / 网易 / QQ），只试它声明支持的平台；单源完整探测 这个源到底能给哪些平台；哪个平台被拒 一个源几秒到几十秒
快速体检
新增按钮		 每源只试第一首匹配平台的基准曲，超时 8 秒，并发 3 这堆源里哪几个还活着 20 个源约 1 分钟
全部自检
新增按钮		 对每个已启用源跑完整自检（同单源逻辑），并发压到 2 每个源分别能给哪些平台 —— 和卡片上单源自检结论一致 明显更慢，20 个源可能几分钟
为什么「全部自检」不能简单地把体检循环一遍：体检模式里 check(id, true) 跑完第一首就 break，它只证明「至少有一首能取」。只支持一个平台的源和三平台全支持的源，在体检结果里长得一模一样。完整自检才会告诉你它在网易上到底行不行。

二、启动自动自检：一条带闸门的后台任务

GATE 1
开关

音源页「启动时自动自检」，默认关。关闭时 maybeAutoCheck() 直接返回，一个请求都不发。

→
GATE 2
进程内一次

autoCheckStarted 标记，同一次冷启动最多触发一次，页面来回切不会重复跑。

→
GATE 3
30 分钟节流

读 v4_auto_check_at，距上次不足 30 分钟直接跳过 —— 连续重启应用不会变成连续打后端。

→
RUN
延迟 8 秒跑体检

等首屏与冷启动取链过去，再在后台跑快速体检（每源一首），不阻塞播放。

为什么不默认开

  • 自检是真实取链，十几个源一起跑就是一小波请求；
  • 后端刚被 403 时，自动重试只会加深风控；
  • 启动阶段最该保证的是「点歌能出声」，不是「先跑完检查」。

打开后你会得到

  • 每次冷启动（间隔 ≥30 分钟）自动刷新一遍源状态；
  • 进音源页时卡片上的红点/绿点已经是最近一轮的结果；
  • 不用记得手动点「体检」，也不会在播放时突然被一堆请求挤占。

四、验证

构建与自检

  • BUILD SUCCESSFUL，verifiedPassed = True，com.yinzhan.music / 1 / 1.0
  • 自检 26 项：PASS 22 / WARN 4 / FAIL 0
  • 新增 V 组，守住三条路径与开关、节流

反向验证

  • 把 check(id, !full) 改成 check(id, true) → V 组 FAIL「两种模式跑出来的其实是同一种」
  • 去掉 autoCheckSources() 判断 → V 组 FAIL「启动自检没读开关」
  • 还原后 PASS
使用建议：刚导入一批源时，先点一次「快速体检」把死源挑出来禁用；对留下来的两三个源再点「全部自检」，确认它们各自能给哪些平台。日常打开「启动自动自检」就够了，不必反复手动跑 —— 体检本身会消耗后端的容忍度。
