Q你的两个问题

「为什么搜歌手点进歌手详情要么都是三十首歌曲要么是五十首歌曲，就一个歌手不可能只有点歌曲，是只能获取到 30 或者 50 首吗？」
「还有酷我还是不能搜出来。」

结论先给：不是接口只能给 30 / 50 首，是代码只取了一页。两个问题都跟上一轮（v2.12）我留下的错误判断直接相关，本版一并纠正。

130 / 50 首从哪来

歌手详情页 ArtistPage.fetchSongs() 的逻辑是「先调平台歌手作品接口，拿不到再退化成按歌手名搜索再筛」。而 PlatformApi.artistSongs() 此前只实现了网易云一个平台，其余四个平台直接返回空数组：

点歌手卡片→ artistSongs()→ 仅 wy 有实现 / 其余返回空
  • 50 首＝网易云走老接口 /api/artist/{id} 的 hotSongs，这个字段固定 50 首热门。实测同一位歌手 musicSize=407，接口不是只有 50 首。
  • 30 首＝QQ / 酷狗 / 酷我 / 咪咕 返回空 → 退化到「按歌手名搜第 1 页再筛」，各平台每页 rn=30 / limit=30 / pagesize=30，筛完往往还更少。
关键：30 和 50 都是代码里写死的「热门 50」和「搜索第一页 30」，不是任何平台的上限。把这两个数当成接口能力，是我上一轮没查链路就直接下结论的结果。

2酷我为什么搜不出歌手

searchArtists() 里 wy / tx / kg / mg 都有分支，唯独 kw 直接返回空。上一轮我在那里留了一句注释：

「酷我公开接口返回单引号非标准 JSON，JSON.parse 会失败，强行解析容易把搜索页整块带崩」——这个判断是错的。

工程里早就有 parseKwItems()，用「按 {"AARTIST" 切块 + 逐字段正则」稳定解析酷我 r.s 的伪 JSON，从不依赖 JSON.parse。实测 ft=artist 返回 20 位歌手，字段齐全：

字段含义实测样例（搜「陶喆」）
ARTIST歌手名陶喆
ARTISTID歌手 ID451
PICPATH头像相对路径240/s4s55/31/1316361792.jpg
BASEPICPATH头像前缀（响应头部）http://img1.kuwo.cn/star/starheads/
SONGNUM作品数502

头像拼成 BASEPICPATH + PICPATH 再升 https，实测 HTTP 200、image/jpeg、10KB 可达。另有一个易踩的差别：歌手搜索（ft=artist）是单引号伪 JSON，作品查询（r.s?artistid=）是标准双引号 JSON，两者必须分开解析——本版分别用 parseKwArtists() 和现成的 parseKwItems()。

核心代码形态：

async artistSongs(artist: ArtistInfo, page: number = 1): Promise<PagedSongs> {
  if (artist.platform === 'wy') return await this.wyArtistSongs(artist.id, p);
  if (artist.platform === 'tx') return await this.txArtistSongs(artist.id, p);
  if (artist.platform === 'kg') return await this.kgArtistSongs(artist.id, p);
  if (artist.platform === 'kw') return await this.kwArtistSongs(artist.id, p);
  return emptyPaged(p);  // 咪咕等无公开接口，交还详情页兜底
}
