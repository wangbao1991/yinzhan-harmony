播放栏上滑展开 · 改成官方一镜到底

v2.5（16 / 2.5）· 本轮唯一主题：把「迷你播放条 → 全屏播放页」从系统模态滑入， 改为 HarmonyOS 官方的 共享元素转场（geometryTransition），并修掉跟手位移被属性动画拖慢的问题。 下面是官方方式的判定依据、实际改动、可播放的对比预览和完整验证结果。

一、官方有四种做法，哪一种符合我们 判定

依据官方《共享元素转场（一镜到底）》与《一镜到底动效开发实践》的分类， 我们这个场景是「底部一条播放胶囊 → 整屏播放页」：不发生路由跳转、前后是同一首歌的界面、 播放状态都在 Player 单例里而不是组件实例里，所以创建新节点开销小。

官方方式适用场景本工程是否合适
② geometryTransition 共享元素转场
两组件绑同一 id + 转场放进 animateTo		 创建新节点开销小；「图标 / 搜索框 / 列表展开」 ✅ 采用。对应官方「图标展开：geometryTransition 接口 + 显示动画」，系统自动插值位置与尺寸
① 不新建容器、直接变化原容器转场开销极小的简单展开 / 收起 ❌ 这正是底栏 stage() 逐帧手算的老路，没有系统插值，容易糊成两团半透明影
③ NodeController 跨容器迁移节点新建对象开销大：视频 / 直播转全屏 ❌ 状态不在节点里，无需迁移；且要自算前后布局位移缩放，官方列为坑最多的方式
④ Navigation 自定义动画转场页面路由跳转（NavDestination 之间） ❌ 播放页是全局浮层，二级页也能打开，不是 NavDestination，套不上

官方对方式 ② 的原话：「系统将调整绑定的两个组件的宽高及位置至相同值，并切换二者的透明度」； 《Navigation 转场动画》还强调 「配置了共享元素转场的页面，同时需要关闭系统默认的转场动画， 否则默认动画会与共享元素动画叠加，导致效果异常」。这两句直接决定了下面的改法。

二、原来为什么不丝滑 根因

  • 没有几何连续性：原实现是 bindContentCover + ModalTransition.DEFAULT， 系统把整页从底部滑上来，迷你播放条完全不参与形变，只是被盖住 —— 本质是「另一张页面盖上来」，不是一镜到底。
  • 状态切换没进动画闭包：playerShow = true 是直接赋值，系统没有机会接管插值。
  • 跟手被缓动追：播放页 .translate({y: dragY}).animation({duration:160}) 把属性动画 挂在每帧变化的位移上。工程自己在 TabBar.onSwipe 的注释里记过同一个坑： 「属性动画的时长在渲染时读一次……实际表现是原地卡住、然后硬跳」。手指和内容之间像隔了一层橡皮筋。
  • 松手有跳变：旧代码在 onActionEnd 里先无条件把 dragY 清零再关闭， 于是「先弹回原位、再开始收拢」。

三、按官方范式落地 改动

集中在 pages/Index.ets 与 ui/pages/PlayerPage.ets，四处要点：

// 1) 同一组件树内互斥出现，绑定同一个 id（不再用独立模态窗口）
if (!this.playerShow) {
  Column() { MiniPlayer() }
    .geometryTransition(this.playerGeomId)
    .transition(TransitionEffect.OPACITY.animation({ duration: 180 }))
}
if (this.playerShow) {
  Stack() { this.playerCover() }
    .geometryTransition(this.playerGeomId)
    .transition(TransitionEffect.OPACITY.animation({ duration: 180 }))
}

// 2) 状态切换放进 animateTo 闭包；3) onFinish 清空 id 防误触发
private setPlayerShow(show: boolean): void {
  animateTo({
    curve: curves.interpolatingSpring(0, 1, 342, 38),  // 官方「图标展开」弹簧曲线
    onFinish: (): void => { this.playerGeomId = ''; }
  }, (): void => {
    this.playerGeomId = PLAYER_SHARED_ID;   // 下次触发前设回
    this.playerShow = show;
  });
}

// 4) 跟手零延迟：translate 上不再挂 .animation()
.translate({ y: this.dragY })
// 松手：达标交给转场且不清零；未达标才用 animateTo 显式回弹

bindContentCover 整段移除 —— 它是独立模态窗口，跨窗口拿不到「组件内隐式共享元素」 的几何连续性，而且默认转场会与共享元素动画叠加。改成同树 if/else 后就是官方示例 1 的标准范式。 打开 / 关闭（点击、下拉、返回键）三处入口统一走 setPlayerShow()，曲线一致。

六、边界与真机确认 须知

  • 本沙箱没有真机 / 模拟器，动效手感无法实测。弹簧参数 (0, 1, 342, 38) 是官方 「图标展开」案例的原值，装到真机后若觉得偏慢或偏弹，只需改 setPlayerShow() 里这一处。
  • 底部栏滚动收起不在本次范围。它属于官方「共享容器转场」，且必须 1:1 跟手 （由 tabBarProgress 逐帧驱动），改成补间动画反而会不跟手，故 Shell.ets 原样保留。
  • v1.9 基线 ZIP 不在本沙箱，SOP 第 6 节的基线 SHA256 复核这轮无法执行；本轮回滚锚点是上面那份 v2.4 隔离快照。
  • 当前签名用 OpenHarmony 公共材料，适用于设备 / 模拟器与产物验收；HarmonyOS NEXT 正式真机仍需 AGC 证书与 profile。
