# 音栈 · 音源协议兼容分析与能力升级报告（整合版）

> 样本：用户上传的「洛雪音源 2.zip」20 个脚本 + [pdone/lx-music-source](https://github.com/pdone/lx-music-source) 仓库 16 种音源、39 个脚本（含 23 个历史版本）。
> 基准：LX Music 桌面版 / 移动版官方自定义音源协议，仓库内 `lx/2.js` 是**明文版官方源**，可直接作为协议基准。
> 方法：源码核对 + 全量脚本特征扫描 + 离线复现实验（`scripts/verify_source_protocol.js`）。**未做真机抓包**。

---

## 一、结论先说

**不是音源不行，是我们应用对音源返回的结果「协议没对齐 + 验得太严」，把本来能用的无损链接判成不合格丢掉了。**

对照官方客户端，差异集中在四层；本次已把前三层修掉，第四层补齐大半：

| 层 | 问题 | 本轮状态 |
|---|---|---|
| ① 下载前二次验货 | 探测请求不带音源给的防盗链头 + `unknown` 格式直接判死 | ✅ 已修（主因） |
| ② `resp.body` 语义 | 返回原始字符串，官方是解析后的对象 | ✅ 已修（双兼容） |
| ③ 音质档位 | 硬编码 5 档，音源声明的母带 / 全景声选不到 | ✅ 已修（动态档位 + 归一化） |
| ④ 桥接 API 缺口 | EVENT_NAMES、version、description、follow_max 等 | ✅ 补齐主要项；binary / 强混淆官方源仍有上限 |

## 二、为什么「同样的音源，别的洛雪软件能下无损」

### 2.1 官方协议长什么样（新增基准）

仓库 `lx/2.js` 是明文版官方源，把协议讲得很清楚：

```js
// 第 18 行：官方标准档位
// 全部的支持值: ['128k', '320k', 'flac', 'flac24bit']
const MUSIC_QUALITY = {...}

// 第 27 行：宿主必须提供的 API
const { EVENT_NAMES, request, on, send, utils, env, version } = globalThis.lx

// 第 42 行：request 回调拿到的 resp.body 是「对象」
request(url, options, (err, resp) => { ... })
const { body } = request
if (body.code == 0) return body.data     // 直接把链接交给播放器/下载器
```

关键三点：

1. **官方客户端不做「下载前二次验货」**——音源给什么链接就用什么，`body.data` 直接进播放器/下载器。
2. **`resp.body` 是解析后的对象**（`body.code` / `body.data`），不是原始字符串。
3. **音质档位由音源 `inited` 上报的 `sources[].qualitys` 决定**，客户端据此动态生成选项；官方只规定 4 个标准值，但**协议允许音源自定义**。

### 2.2 主流第三方音源扩展了档位（新证据）

16 种音源里，高规格档位的分布：

| 档位 | 出现该档位的音源数 | 代表音源 |
|---|---|---|
| `hires` | 5 | helloworld、ikun、jiexiang、qdy、xinghai |
| `master` | 5 | 同上 |
| `atmos` | 5 | 同上 |
| `atmos_plus` | 3 | helloworld、jiexiang、xinghai |
| `flac24bit` | 7 | 多数主流源 |
| `24bit`（非标准别名） | 1 | 全豆要旧版 |

例如 ikun 源声明：

```js
const MUSIC_QUALITY = JSON.parse(
  '{"kw":["128k","320k","flac","flac24bit","hires"],' +
   '"wy":["128k","320k","flac","flac24bit","hires","atmos","master"]}'
)
```

杰翔源头部直接写着「全平台支持 flac，wy / qq / kw / kg 支持母带」，星海写着「最高支持母带」。**别的洛雪软件会把这些档位全部列出来让用户选**，我们应用硬编码 5 档，母带/全景声根本没机会被请求。

### 2.3 四层原因（整合上一轮结论）

#### ① 下载前的「二次验货」把无损链接拒了 —— 主因

| | 别的洛雪软件 | 修复前的音栈 |
|---|---|---|
| 拿链接后 | 直接交给播放器 / 下载器 | `probeAudioEx()` 发 `Range: bytes=0-0` 探测 |
| 请求头 | 带音源给的 headers | 硬编码 `User-Agent: okhttp/4.10.0`，**`parsed.headers` 完全没传进探测** |
| 格式判定 | 信任音源 | 必须靠 Content-Type / 后缀 / 体积估出 `flac` |
| 下载 | 不强制验货 | `resolve(..., strict=true)`，要求 `probe.format === 'flac'` |

矛盾点很直白：**下载请求带音源给的 headers，探测请求不带**——探测先挂了，根本走不到下载。

新证据：仓库里音源返回 `headers` 的密度很高（杰翔 87 处、HelloWorld 13 处、星海 7 处、全豆要 5 处），中转 / 聚合 API 几乎都靠 `Referer` / `Cookie` / `X-Request-Key` 鉴权，不带就回 403 或一段 HTML。

而大量中转链接是 `application/octet-stream` + 无 `.flac` 后缀（形如 `/wy/wy.php?type=mp3&id=...&level=...`）。旧的 `detectFormat` 返回 `unknown`，严格模式直接判死刑。离线复现：

| 典型无损链接 | 旧判定 | 旧结果 | 新结果 |
|---|---|---|---|
| `audio/flac` + `.flac` 直链 | flac | 通过 | 通过 |
| `octet-stream` + 无后缀中转 | unknown | **拒绝** | 放行 |
| `octet-stream` + `?type=flac&level=hires` | unknown | **拒绝** | 判 flac，放行 |
| `octet-stream` + `?br=999`（24bit） | unknown | **拒绝** | 判 flac，放行 |
| `audio/mpeg` 头、实际是 mp3 | mp3 | 拒绝 | 仍拒绝（真虚标） |
| 防盗链返回 HTML | 前置拦截 | 拒绝 | 仍拒绝 |

#### ② `resp.body` 没按官方语义解析 —— 部分音源完全拿不到链接

桥接页原先返回 `body: payload.data`（**原始字符串**）。但音源写法分两派：

| 派别 | 音源 | 写法 | 修复前 |
|---|---|---|---|
| 对象派 | ikun(13)、qdy(14)、xinghai(23)、huibq(4)、juhe(2)、jiexiang(1) | `body.code` / `body.data` / `body.url` | ❌ `unknow error` |
| 字符串派 | 全豆要、聚合音源 | `body.trim()` 后自己 `JSON.parse` | ✅ 能跑 |

括号里是各脚本里直接取 `body.xxx` 的次数。ikun / huibq / juhe 会 `isNaN(Number(body.code))` → 直接抛错，**连链接都取不到**。

注意不能简单改成纯对象：全豆要 / 星海里有 `body.trim()`、`body.toString('utf-8')` 的兼容写法，纯对象会抛 `body.trim is not a function`。所以本轮用的是 **String 包装对象 + 挂载解析字段** 的双兼容方案（见 3.2）。

#### ③ 音质档位：不只是表不全，是机制错了

- `QUALITY_ORDER` 硬编码 `['flac24bit','flac','320k','192k','128k']`，设置页 / 播放页只列这 5 档；
- `qualityRank('master')` / `qualityRank('atmos')` 返回 1（等同 128k），导致 `canTop()` 误判、`strictChain` 错误降级；
- `isLossless()` 只认 3 档，母带 / 全景声不算无损；
- `SourceRepo` 其实**已经动态收集了音源 `inited` 上报的 qualitys**，但对外排序与 UI 仍被硬编码表截断，未知档位还会被 `qualityLabel` 显示成「128K」；
- 全豆要旧版用 `24bit` 别名，档位名对不上。

#### ④ 桥接 API 的小缺口（次要）

- `EVENT_NAMES` 只有 4 个，缺 `updateAlert`（仓库 3 个音源使用、官方 `lx/2.js:231` 也用），`send()` 发出的自定义事件在原桥接层被静默丢弃；
- `version` 写死 `'2.0'`，而官方把它拼进 `User-Agent: lx-music-mobile/${version}`，部分服务端按版本切分支；
- **`currentScriptInfo.description` 为空是隐患**：官方源 `lx/2.js:255` 用 `md5(name + description)` 做防篡改校验，不匹配会进入 `while(true)` 死循环把沙箱拖垮；
- `follow_max` 未实现（写死 4 次跳转），而官方源 / ikun / 杰翔 / 全豆要都指定 `follow_max: 5`；
- `responseType` / `binary` 未实现（本轮留了桥接侧钩子，原生侧未启用）。

### 2.4 不是问题的

音源包里约 21% 是 `http://` 明文链接（长青 / 杰翔 / 全豆要 / 星海等），工程已通过 `module.json5` 的 `ohos.network.security.config` 元数据 + `cleartextTrafficPermitted: true` 正确放行，这一层没问题。

## 三、本轮落地的能力升级

### 3.1 探测层：不再误杀无损链接

| 文件 | 改动 |
|---|---|
| `core/Http.ets` | `probeAudioEx(url, duration, extraHeaders?)` 新增第三参数；把音源返回的 headers 合入探测请求（音源有 User-Agent 时优先用它的）；`detectFormat` 新增查询参数线索识别（`?type=flac` / `br=999` / `level=hires` → flac，`?type=mp3` → mp3） |
| `core/Resolver.ets` | 探测时传入 `parsed.headers`；严格校验从「必须 `format === 'flac'`」改为**只拒绝明确有损证据**（mp3 / m4a / ogg），`unknown` 放行；`actualQuality` 对 unknown 按请求档位记，不再擅自降标成 320K；`strictChain` 加 5 档上限防止变慢 |
| `core/Downloader.ets` | `format === 'unknown'` 且请求无损时按 `.flac` 存，避免无损文件被写成 `.mp3` |

设计取舍：**体积 / 试听片段检查、HTML 前置拦截、明确 mp3 头拒绝全部保留**——这些是真有用的防虚标；放开的只是「认不出格式就判死」。

### 3.2 桥接层：协议对齐（双兼容 body）

`resources/rawfile/lx_bridge.html`：

- 新增 `makeBody(raw, headers)`：按 Content-Type / 内容形态解析 JSON，返回 **String 包装对象并挂载解析出的字段**。于是 `body.code` 能取到、`body.trim()` / `body.toString('utf-8')` / `JSON.parse(body)` 也都还能用；非 JSON 响应保持纯字符串；
- `resp` 额外提供 `rawBody` 原始文本；
- `EVENT_NAMES` 补 `updateAlert` / `showConfigView`；
- `version` 改为 `'1.7.0'`（对齐移动端协议版本），`currentScriptInfo` 补 `description`（修掉官方源死循环校验隐患）；
- 预留 `binary` 分支（原生返回 base64 时转成 `Uint8Array`）。

`core/LxRunner.ets`：

- 新增 `case 'event'`，把 `updateAlert` 转成日志，不再静默丢弃；
- 支持音源指定的 `follow_max`（上限 10），默认仍为 4。

离线验证结果（真实 `makeBody` 实现抽取执行）：

| 音源写法 | 修复前 | 修复后 |
|---|---|---|
| ikun / huibq `body.code` | ❌ unknow error | ✅ code=0 |
| juhe `body.data` | ❌ 缺失 | ✅ |
| 星海 `body.url` | ❌ 缺失 | ✅ |
| 全豆要 `body.trim()` + JSON.parse | ✅ | ✅ 不回归 |
| 星海 `body.toString('utf-8')` | ✅ | ✅ 不回归 |
| 非 JSON（HTML）保持字符串 | ✅ | ✅ |

### 3.3 音质体系：动态档位 + 别名归一化

`common/Constants.ets`：

- `QUALITY_ORDER` 扩为 9 档全集：`master > atmos_plus > atmos > hires > flac24bit > flac > 320k > 192k > 128k`；
- 新增 `BASE_QUALITY_ORDER`（基础 5 档常驻）、`normalizeQuality()`（`24bit`→`flac24bit` 等别名）、`qualityOptions()`（基础档常驻 + 音源声明的扩展档才出现）；
- `qualityRank()` 补全 9 档映射、`isLossless()` 覆盖全部无损 / 高规格档、`qualityLabel()` 补「母带 / 全景声+ / 全景声 / Hi-Res+」。

`core/SourceRepo.ets`：`getQualities()` 归一化后按全集排序，`item.qualities` **保留音源上报的原始档位名**。

`core/Resolver.ets`：新增 `sourceQuality(item, internal)` 反查——反问音源时用它自己认识的那个原始字符串（旧版全豆要写 `24bit` 也能正确取链）；`availableQualities()` 归一化，降级链比较不再失真。

`Settings.ets` / `SettingsPage.ets` / `PlayerPage.ets`：说明文案与选项列表同步，**母带 / 全景声等只在音源声明支持后出现**，不凭空造选项。

### 3.4 新增可复现自检

`scripts/verify_source_protocol.js`：从 `lx_bridge.html` 抽取真实的 `makeBody` 实现执行，回归验证双兼容、格式判定、音质表三组用例。`node scripts/verify_source_protocol.js` 当前输出「全部通过」。

## 五、仍存在的限制（如实说明）

1. **官方独家源 `lx/5~7.js` 跑不起来**：这些版本是重度混淆 + 服务端下发配置（`signSalt` / `fingerprint` / `apiKey`），依赖宿主特征与签名校验，WebView 沙箱无法完全模拟。仓库里 `lx/2.js` / `3.js` 是明文版，可作为协议参照但同样带 `name+description` 防篡改死循环校验——本轮已补 `description`，仍不保证哈希精确匹配。
2. **`responseType: 'arraybuffer'` / `binary` 请求**：桥接侧已留钩子，原生 `LxRunner` 仍固定按 STRING 取响应。仓库 16 个音源里没有发现强依赖，故本轮未启用，避免引入新的编解码风险。
3. **第三方 VIP 解析接口本身有时效和风控**：即使协议完全对齐，也不保证 100% 取链成功；失败时会走既有的换源 / 降级 / 报错链路，不会静默给低音质。
4. **签名**：HAP 仍使用 OpenHarmony 公共签名材料，HarmonyOS NEXT 真机安装需要在 AGC / DevEco 为 `com.yinzhan.music` 生成调试 profile 重签。

## 六、建议的后续验证顺序

装机导入一个**对象派**音源（如 ikun / 星海）与一个支持母带的音源（如杰翔 / 星海），依次确认：

1. 音源管理页能正常 `inited` 并列出平台；
2. 设置页 / 播放页出现「母带」「全景声」等档位；
3. 选 `FLAC` 或 `Hi-Res` 下载，能拿到完整文件、扩展名正确；
4. 播放页点播放能出声（不再因探测缺 headers 报「取链失败」）。

若某一步仍失败，把音源名 + 失败提示发回来，可以按提示里的首选音源 / 原因继续定位。

## 七、第三轮：运行时能力对齐（为什么安卓洛雪能用，我们限制多）

> 触发：用户实测「星海能下酷我 FLAC，其它平台基本都报错」，追问「安卓洛雪大多数音源都能下载，为什么我们限制那么多」。
> 方法：桥接层 / 原生网络层 / 下载校验逐行核对 + 20 个本地音源脚本全量特征扫描 + 官方明文基准 `lx/2.js` 对照。

### 7.1 结论

**差距主要不是鸿蒙平台做不到，而是我们自己的桥接实现与策略选择造成的**。官方安卓洛雪的核心优势是「默认 UA + 不二次验货 + 全源并发」，这三点都能在应用端补齐；本轮已全部落地。剩下的失败才真正由第三方音源后端决定。

### 7.2 与官方的关键差异

| 维度 | 安卓洛雪（官方） | 修复前的音栈 | 本轮 |
|---|---|---|---|
| 音源运行时 | 宿主注入 `globalThis.lx`，脚本互不干扰 | 一个 ArkWeb 页面塞进所有音源，共用 `window.lx`，`__setActive` 固定指向首选 | 调用期间切到目标实例 + 引用计数恢复 |
| 脚本内 HTTP 默认 UA | 每个请求带 `lx-music-mobile/${version}` | **不补 UA**，20 个脚本里 8 个空 UA 裸奔 | 补 `lx-music-mobile/1.7.0` + `Accept: */*` |
| HTTP method | 完整 | 只认 GET/POST/PUT，其余退化成 GET | 补全 8 种，PATCH 走 POST + 覆盖头 |
| 二进制响应 | `arraybuffer` | 固定 `STRING`，`binary` 钩子空转 | `ARRAY_BUFFER` → base64 → `Uint8Array` |
| 多个 request handler | 全部可注册 | `__emit` 只跑 `handlers[0]` | 遍历 + 竞速取第一个有效结果 |
| 下载前验货 | 不做，`body.data` 直接进下载器 | 每次发 `Range: bytes=0-0` 探测 | 默认跳过，改为落盘后验文件头 |
| 单源超时 | 官方源 8s / 聚合包总 30s | 6s | 12s |
| 多源策略 | 全启用音源并发竞速 | 首选独占 + 补位；「只用首选」可关掉全部补位 | 健康度降权 + 连续失败强制补位 |

### 7.3 量化证据（20 个本地脚本）

| 宿主能力 | 依赖脚本数 | 修复前后果 |
|---|---|---|
| 默认 UA | **8 个完全不设**（长青SVIP、lx-music-source-v7、野花/野草/念心/忆音/屿溪） | 聚合接口 403 / 404 |
| `responseType: arraybuffer` / `binary` | 2 | 拿不到二进制响应 |
| 非 GET/POST method | 2 | 静默退化成 GET |
| 运行时读 `globalThis.lx` | 11（合并音源 35 处） | 异步回调串到别的音源实例 |

星海脚本自己补了 `'lx-music'` UA（`星海-music-sourcev2.3.15.js:281`），所以它的酷我本地直连能跑；长青SVIP 在「不设 UA」名单里，请求更容易被拒 —— 这解释了「为什么偏偏星海能用」。

### 7.4 本轮落地（8 项）

| 文件 | 改动 |
|---|---|
| `resources/rawfile/lx_bridge.html` | `__emit` 遍历所有 handler 并竞速；调用期间把 `globalThis.lx` 切到目标实例、结束后引用计数恢复（`baseLx` / `lxCallCount`） |
| `core/LxRunner.ets` | 补默认 UA / Accept；`requestMethod()` 补全 8 种 method + PATCH 覆盖头；`ARRAY_BUFFER` → `toBase64()` → `payload.binary` |

### 7.5 设计取舍

「默认信任音源」不是放弃防虚标，而是**把验货从下载前挪到下载后**：

- 保留：试听片段体积校验（>1 分钟却 <50KB 判失败）、HTML / JSON 错误页拦截、写盘后按真实容器改扩展名；
- 请求无损却验出 mp3 / m4a / ogg 时，如实把「实际音质」标成 128K 并按 `.mp3` 保存，不静默改成 `.flac`；
- 需要下载前就挡住虚标的，可在音源选项里打开「下载前严格验音质」。

## 八、第四轮：让装进去的十几个源真正都参与

### 8.1 现象

真机反馈：装了十几个音源，播放《江南》时顶部只显示「全豆要[聚合音源]」，下方红色「音频准备失败」——看起来应用只试了一个源。

### 8.2 先定性：这次不是取链失败，是播放器准备失败

`Player.ets` 里 `handleFail('音频准备失败')` 来自 `AVPlayer.prepare()` 的失败回调（`stateChange → initialized → prepare()`）。能走到这一步，说明 `Resolver.resolve()` **已经成功返回了链接**，顶部那个音源名正是 `result.from`。

所以「只试一个源」的责任不在音源脚本、也不在桥接层，而在**链接被选中之后**。上一轮补的「全源并发」只在取链阶段生效，取链之后没有任何回退机制。

### 8.3 四个叠加的代码级根因

| # | 位置 | 旧行为 | 后果 |
|---|---|---|---|
| 1 | `Resolver.trySources()` 阶段 1 | 首选在 `PREFERRED_WINDOW_MS = 3000` 内返回**任意**链接就 `return early` | 其余十几个音源**根本没被启动** |
| 2 | `Resolver.fetchFromSource()` | 播放路径探测失败一律 `probe = null`「信任音源」，403 / 404 / 防盗链 HTML / 试听片段照样算成功 | 坏链接在独占窗口里抢跑胜出 |
| 3 | `Resolver.firstUsable()` | 竞速只 `resolve(result)` 第一条，其余 Promise 的结果直接丢弃 | 没有任何备用链接 |
| 4 | `Player.handleFail()` | prepare 失败只报错 + 自动跳下一首 | 从不回头试其它音源已经给过的地址 |

第 1 条是关键：上一轮的「全源并发」是**阶段 2** 才启动的，而首选只要在 3 秒内吐出一条链接（哪怕是 404 的错误页地址），阶段 2 整段都被跳过。截图里「全豆要[聚合音源]」恰好是个返回很快的聚合源，于是稳定复现。

### 8.4 本轮落地（4 项）

| 文件 | 改动 |
|---|---|
| `core/Resolver.ets` | 新增备用链接池 `alternates`：每个成功取到链接的音源都 `offerAlternate()` 留一份，按「探测是否通过 + 音源健康度」排序；`takeAlternative()` 供播放失败时换链，同时清掉失败链接的 15 分钟缓存并给该音源降权 |
| `core/Resolver.ets` | `isFatalProbe()`：播放路径探测明确判坏（4xx/5xx、HTML/JSON、试听片段、非法地址、跳转异常）时**淘汰该链接**，让其它音源有机会；探测本身失败（超时 / `HTTP 0` / 判断不了）仍信任音源。只有 1 个候选源时 `lenient = true`，不判死，避免防盗链误报把唯一机会也砍掉 |
| `core/Resolver.ets` | 失败提示补「共 N 个音源参与取链」，`ResolveState.candidateCount` 按实际进入候选的数量累计 |
| `core/Player.ets` | `handleFail()` 在播放器阶段失败时先 `takeAlternative()` 换链重试（上限 `MAX_SOURCE_SWITCH = 3`），顶部显示「音源名 · 换源 1/3」；切歌重置计数、清失败链接缓存；备用池空才走原来的报错 / 自动跳歌 |
| `ui/pages/SourcesPage.ets` | 音源选项上方新增「已启用 X 个 · 已加载 Y 个」实时统计，并说明只有已启用且脚本加载成功的音源才参与取链 |
| `scripts/verify_source_protocol.js` | 扩到 A~H 八组；H 组直接抽取 `offerAlternate` / `takeAlternative` / `isFatalProbe` 的真实实现执行 |

### 8.5 新的播放失败链路

> 坏链接不再抢跑 → 所有可用音源并发 → 每条链接都进备用池 → 竞速取最快的一条交给播放器 →
> 若 `prepare()` 失败，自动换到池里**探测通过**的下一条（最多 3 次），顶部如实显示换源 →
> 池空才报错并跳下一首，且报错里写明「共 N 个音源参与取链」。

「默认信任音源」没有被推翻：被淘汰的是**探测明确判坏**的链接，而不是「探测不了」的链接；单个音源时依旧信任。验货策略仍以落盘后验文件头为准。

### 8.6 用户侧自查

设置 → 音源管理 → 音源选项上方会显示「已启用 X 个 · 已加载 Y 个」：

- **Y 明显小于 X**：有脚本没加载成功（语法报错、`inited` 没到、被沙箱拦下），这些不会参与取链，需要删掉重导或换版本；
- **Y ≈ X 但仍失败**：说明确实用上了全部音源，剩下的就是第三方后端 403 / VIP 风控，属于上一章 7.7 的范围；
- 播放时若看到「· 换源 1/3」，说明自动换链已生效。
